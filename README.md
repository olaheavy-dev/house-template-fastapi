# house-template-fastapi

The FastAPI layer of my Copier project templates. It adds a Python backend under `backend/` to a project generated from [house-template-base](https://github.com/olaheavy-dev/house-template-base), and plugs the backend's checks into the base `make check`, CI, CodeQL and Dependabot.

## Use it

```sh
copier copy --trust gh:olaheavy-dev/house-template-base my-app      # choose the fastapi stack
cd my-app && git init -b main && git add -A && git commit -m "chore: start from house-template-base"
copier copy --trust -a .copier-answers.fastapi.yml gh:olaheavy-dev/house-template-fastapi .
cp backend/.env.example backend/.env
# With the model gateway (llm: langchain, the default with the database): in backend/.env set
# LLM_MODEL and EMBEDDING_MODEL
# (<provider>:<model-id>); the template picks none. Add each model's prices to
# backend/src/app/llm/prices.py first, with the date you read them and the provider's pricing page
# (the app refuses to start otherwise).
make install && make check      # the tests need Docker, unless both database and storage are off
make db-up && make migrate && make dev   # with the database (the default; see Options)
make storage-up                    # for file storage (the default; see Options), with STORAGE_BUCKET set in backend/.env
make dev                           # with neither part: just the API
```

The layer checks the base answers (the fastapi stack) and copies `container_images` from them into its own answer in `.copier-answers.fastapi.yml`, which is what lets `copier update` work; template files never read the base answers. `copy` and `recopy` refuse without `.copier-answers.base.yml`; `update` cannot check for it and carries on. The refusal comes after an interactive answer or `-d container_images=...` (without either, Copier stops earlier with "Question container_images is required"; the interactive flow is untested), and by then files may already be written. If this directory had no uncommitted work before the run (check `git status`), undo it with `git clean -fd` and `git checkout .`; otherwise remove only the files the run added. Then apply the base first and run it again.

## Options

Answers that switch parts of the backend on or off. Each default keeps today's output.

| Answer | Default | When off |
|---|---|---|
| `database` | `true` | No PostgreSQL, SQLAlchemy or Alembic migrations, and so no model gateway either (the gateway keeps its budget and agent checkpoints in the database, so `llm` becomes `none`): no `app/db.py`, `app/models.py`, `migrations/`, `compose/db/compose.yaml`, `tests/db.py`, `tests/test_db.py`, `make db-up`, `migrate` or `migration`, the `db` extra in the image and make targets, the database settings, and the database rules text, plus everything `llm: none` removes. With both parts off, `make check` needs no Docker |
| `llm` | `langchain` with the database, `none` without | `none` or `langchain`. `none` leaves out the **model gateway**: no `app/llm/`, `app/prompts/`, `llm-contracts.toml`, `tests/models.py`, `tests/recording.py`, `tests/wire.py`, the model tests, evals or cassettes, no model, embedding, key, agent, redaction or tracing settings, `make llm-report`, `record-llm` and `eval`, the `langchain` extra in the image and make targets, and the model rules text. The database stays (with its migrations; see below). `langchain` is LangChain and LangGraph with the daily budget, prompts and agent checkpoints in PostgreSQL, so it is refused without `database: true`. `maf` (Microsoft Agent Framework) joins as a third choice in #35 |
| `storage` | `true` | No `app/storage.py`, storage settings, `.env.example` entries, readiness check, storage tests, RustFS compose service, `make storage-up`, storage rules text or `boto3` in the image and make targets |

```sh
copier copy --trust -a .copier-answers.fastapi.yml -d storage=false gh:olaheavy-dev/house-template-fastapi .   # likewise -d database=false (which also means llm=none) or -d llm=none
copier update --trust --defaults -a .copier-answers.fastapi.yml -d storage=false   # an existing project; commit first (without --defaults it asks the other questions again)
```

How it works: files that exist only with an answer are listed in `copier.yml` `_exclude` as Jinja patterns, and `copier update` deletes them when the answer turns off (tested; your own files and `backend/uv.lock` stay). Files that change with an answer are templates (`x.jinja`) with an all-on plain twin next to them so the template's own tests run; a test keeps each twin equal to its template. Dependencies are optional extras in the one plain `backend/pyproject.toml` (`[project.optional-dependencies]`: `db` comes with the `database` answer, `langchain` with `llm: langchain`, `storage` with `storage`), so Dependabot still updates it. The extras are not tied together in `pyproject.toml`: `llm: langchain` needs `database: true` (the question refuses it otherwise), and the make targets and the image always install `db` with `langchain`. `make install`, the other make targets and the image install only the extras the project answered for (`EXTRAS` in `mk/fastapi.mk`, `--extra` in the Dockerfile); the lockfile holds all of them. **Commit first.** `-d database=true` alone does not bring the gateway back once the answers file records `llm`, which the first 0.8.0 update does. A project from v0.7.1 with `database: false` has no recorded `llm` yet, so its first update with `-d database=true` gets the default `langchain` and the gateway returns: pass `-d llm=none` to keep it off. To turn it on, add `-d llm=langchain` too (`-d database=false` alone also sets `llm: none`). When you turn the database off, see "Turning the database off" under Upgrading; for the gateway, "Upgrading to 0.8.0". When you turn storage off, `copier update` deletes the template's storage files even if you edited them (`app/storage.py`, `tests/storage.py`, `tests/test_storage.py`, `compose/storage/compose.yaml`); your own files and `backend/uv.lock` stay, and you can recover edits from git. It does not drop what is in a bucket. Your own code that imports `app.storage` fails `mypy`, your own tests that use the `storage_settings` fixture fail in pytest, and a running RustFS container and the `storage-data` volume are left behind as orphans (`docker compose down --remove-orphans`, then remove the volume). Afterwards run `make lock && make install && make check`.

## Upgrading

**Breaking: the database and model packages moved into extras.** `alembic`, `sqlalchemy`, `psycopg`, `pgvector` and the rest of the database stack are now in the `db` extra, and `langchain`, `langgraph`, `langsmith` and the provider packages in the `langchain` extra; only `fastapi`, `pydantic-settings` and `structlog` stay in the main dependencies. `make install`, `make dev`, `make check` and the Docker image install them for you. A plain `uv sync`, `pip install .` or your own Dockerfile no longer gets them: add `--extra db --extra langchain` (and `--extra storage`). After `copier update --trust -a .copier-answers.fastapi.yml`, run `make lock` (your `uv.lock` is yours). Projects made before the `database` question existed take `database: true` on update, so nothing is removed. Packages moved; none were added.

**Turning the database off** (`database: false`, which also sets `llm: none` and removes the model gateway):

1. Commit everything first.
2. Projects from v0.6.1 or earlier must first `copier recopy` to v0.7.0 (#49, "Upgrading to 0.7.0" below).
3. `copier update` never touches a database: tables are never dropped. To drop them, run `uv --directory backend run --locked --extra db --extra langchain alembic downgrade base` BEFORE updating, while Alembic and the migrations still exist (with `llm: none`, leave out `--extra langchain`: nothing imports the model packages); it removes every template and project table.
4. Run `copier update --trust --defaults -a .copier-answers.fastapi.yml -d database=false` (without `--defaults` it asks every question again).

What the update deletes: the template's database and gateway files, even ones you edited (recover them from git): `app/db.py`, `app/models.py`, `app/llm/`, `app/prompts/`, `migrations/`, `llm-contracts.toml`, `compose/db/compose.yaml`, `tests/db.py`, `tests/wire.py` and the database and model tests, evals and cassettes. Your own files stay. Your own migrations in `backend/migrations/versions/` are left behind; `make check` still lints them with ruff but no longer type-checks them (Alembic is no longer installed): delete or move them. Your own tests that use `db_session` or `db_client` fail in pytest (the fixtures are gone), and code that imports `app.db`, `app.models` or `app.llm` fails `mypy`. Remove `DATABASE_URL` and the model settings from `backend/.env` (a leftover value is ignored). Run `docker compose down --remove-orphans`, then remove the `db-data` volume. Afterwards run `make lock && make install && make check`. Turning it back on restores the template's versions of those files, not your old edits. If you edited a twin file (`main.py`, `settings.py`, `log.py`, `tests/conftest.py`, `.env.example`, `app/api/__init__.py`, `app/models.py`, `migrations/env.py` or migrations 0002 to 0006), expect conflict markers in it after an update (untested).

**After the recopy below (v0.6.1 and earlier) or an update, from a release before this one (breaking):** `boto3` moved from the main dependencies to the `storage` extra. `make install`, `make dev`, `make check` and the Docker image install it for you; anything that installs the backend without them (a plain `uv sync`, `pip install .` or your own Dockerfile) no longer gets `boto3`, and importing `app.storage` fails. Use `uv sync --extra storage`, or add `--extra storage` to your own install commands. After `copier update --trust -a .copier-answers.fastapi.yml`, run `make lock`: your `uv.lock` is yours and is not rewritten. Projects made before the `storage` question existed take `storage: true` on update, so nothing is removed. The compose services moved to `backend/compose/db/compose.yaml` and `backend/compose/storage/compose.yaml`, included by `backend/compose.yaml`.

From v0.7.0 on, update the layer with `copier update --trust -a .copier-answers.fastapi.yml`. `--trust` is required: Copier refuses any template that has `_tasks` without it, even when the task does not run in an update. The project owns `backend/uv.lock`, so after an update that changes dependencies, run `make lock` and commit the lockfile before `make install`. The update prints a harmless `MissingFileWarning` for `.copier-answers.base.yml`.

If the base's `container_images` changes, the next update follows it: it deletes `.github/workflows/publish-api.yml` when it turns off and adds it when it turns on. If you edited that file, expect a conflict (untested).

Projects made from v0.6.1 or earlier cannot `copier update` (their old version refuses without the base file; #49). Move them once with `recopy`, then update normally. The steps, and what else changed in 0.7.0, are in "Upgrading to 0.7.0" below.

## Upgrading to 0.9.0 (personal-data redaction, #78)

In order: 1. commit everything; 2. `copier update --trust --defaults -a .copier-answers.fastapi.yml`; 3. `make lock && make install`; 4. `make migrate` (new revision 0006); 5. `make check`. This part is for projects with `llm: langchain`; with `llm: none` the only change is an empty revision 0006 that keeps its place in the chain.

**Breaking (`feat!`).** `gateway.model()` now returns a `RedactingChatModel` (`app/llm/langchain/redaction.py`), a chat model of its own around the provider's, with redaction on by default, and the text `gateway.embeddings()` sends is cleaned the same way (item 7). Decision [0006](docs/decisions/0006-personal-data-redaction-in-the-core.md) has the design and the sources.

1. **The type changed.** `isinstance(gateway.model(), ChatOpenAI)` (or `ChatAnthropic`, or `BaseChatOpenAI`) is now `False`; the provider model is `gateway.model().inner`. `_llm_type`, `profile`, `model_name`, `_get_ls_params` and `_identifying_params` come from the provider model, and a request with nothing to redact is byte for byte the request the provider model would have sent, for `ainvoke`, `astream`, `bind_tools`, every structured-output method and every agent strategy (tests compare them). The one known difference a caller can see: `create_agent` probes `isinstance(model, BaseChatOpenAI)`, which is false for the wrapper, so it no longer adds a redundant `strict=True` where it did; no request body differs. The sync methods (`invoke`, `stream`) raise: the gateway already required `await`.
2. **It is on by default.** Text that holds an email, a UK phone number, a national insurance number, an IBAN, a sort code or account number (with those words nearby), a card number, an NHS number or a date of birth (with context), or a value you name, reaches the provider as a placeholder such as `[EMAIL_1]`, and the answer, tool-call arguments, structured fields and streamed text get the originals back. A prompt that already holds such values will change on the wire. Values inside tool-call arguments and JSON text are matched with their field name in front (`date_of_birth`, `account`, `sort_code` and `NHS` fields, in any case style), and JSON text is decoded first, so a known value that holds a quote, a backslash or a non-ASCII character is found in it. This context-gated detection only works when a field name, a `label`/`name`/`field`/`key`/`title` beside a `value`, or a tool's name says what the value is (`birthDate`, `account_no`, `nhsNumber`, `sortCode`, `get_date_of_birth`): a value under a neutral name such as `ref` is not treated as personal data (a known miss, #97). The same rule can over-match prose: "company accounts ... No. 12345678" (the word `accounts` within about 30 characters before an 8-digit company number) replaces the number with `[ACCOUNT_n]`, so the model loses that reference while the user still sees it restored (a known false positive, #97). JSON keys are checked as text too. `LLM_REDACTION=off` restores the old behaviour exactly (no wrapper, no mask on traces, `redacted_count` NULL); `LLM_REDACT_KINDS` chooses the detector kinds (default all nine; a name no detector has stops the app starting).
3. **A new 503.** If redaction fails (a detector raises, or anything else goes wrong while the request is prepared), nothing is sent; so does JSON text nested more than about 1,000 levels deep in a stored tool result, which makes every later call on that thread a 503: the request gets a 503 with no value in it, and no `llm_call` row is written. Detectors you add in `app/llm/redaction_rules.py` now run on every model call, so keep them linear time (#94).
4. **Migration 0006** adds `llm_call.redacted_count` (nullable: NULL is "redaction was off", 0 is "ran and found nothing"). A database that had the gateway's tables and ran this release under `llm: none` is stamped at 0006 without the column. After turning the gateway back on, run `uv --directory backend run --locked --extra db --extra langchain alembic stamp 0005`, then `make migrate`; `backend/tests/test_llm_migrations.py` runs that recipe against a real database (the recipe for a database that never had the tables, `stamp 0001`, is unchanged).
5. **Tell the app what it knows.** Wrap each model call in `async with redaction_scope(known={"NAME": [user.full_name]}, allow=[property_address]): ...`. Without a scope only the pattern detectors run; a name is never guessed.
6. **LangSmith.** With redaction on, the gateway builds one LangSmith client whose anonymizer masks every string in a run's inputs, outputs, metadata and errors, sets it as the process-wide client (`langsmith.configure`), and uses it for its own tracer, so tracing that starts from `LANGSMITH_TRACING` or from a graph is masked too, even when `LANGSMITH_TRACING` is off in the settings. `langsmith.configure(client=...)` replaces any process-wide client your app set itself, so that client's own settings (hiding, an anonymizer of yours) are lost: build your client from the gateway's, or pass yours to the tracers you attach. `LANGSMITH_HIDE_INPUTS` and `LANGSMITH_HIDE_OUTPUTS` still win. Shutdown now flushes that client (before, the gateway's own client was not flushed). A `LangChainTracer(client=...)` you pass in a call's config records what its own client is given.
7. **Embeddings are cleaned too, one way.** With redaction on, every text `gateway.embeddings()` sends (`aembed_documents` and `aembed_query`) is cleaned first, by the same detectors and the same `redaction_scope`, each text on its own: placeholders are numbered inside a text, so a text's vector depends only on the text and its scope, never on the texts around it or on where the price limit cuts the batches. The vectors come back, so nothing is restored and no mapping is kept. What this changes:
   - **Re-embed what you stored.** A vector made from a text that holds a matching value changes (the vector is now of the cleaned text). Vectors made before the update were made from the original text; re-embed every stored text that may hold personal data, or queries will be compared with vectors of a different kind of text.
   - **Embed documents and their queries under the same `redaction_scope`.** Ingest and query use the same `known` and `allow` values for the same person, or a name removed at ingest is left in the query (and the other way round).
   - **Vectors carry no identifiers.** Look an exact email, phone or reference up in your own columns, not through the vectors. Property text (rent, dates, reference numbers, addresses you `allow`) is unchanged: the repository's must-not-change corpus is embedded as it is.
   - **Inputs are plain text.** There is no JSON field context for an embedding input, so a date of birth or an account number is found only when a word before it says what it is.
   - **A new 503 and a new 422 edge.** If a text cannot be cleaned, nothing is sent and no `llm_call` row is written (the 503 of item 3). A placeholder can be longer than the value it replaces (`[NAME_1]` for a two-letter name), so a text just under the price's `max_prompt_tokens` can go over it once cleaned: that text gets the existing 422 (`PromptTooLong`), checked before anything is reserved.
   - **Rows.** Each batch's row counts the values replaced in its texts: 0 when redaction ran and found nothing, NULL only with `LLM_REDACTION=off` (rows written before the upgrade are NULL, because the column is new).
   - **Direct use.** `GatewayEmbeddings(...)` and `app.llm.core.embeddings.embed(...)` take a required keyword-only `redactor` (`gateway.redactor`, or `None` for off), so forgetting it is a `TypeError` and never a silent leak. The embeddings clients of LangChain's own (`init_embeddings`, `OpenAIEmbeddings`, `AzureOpenAIEmbeddings`) and a second way to OpenAI's embeddings request send the original text and skip the budget. A test (`backend/tests/test_llm_redaction_embeddings.py`) catches the usual ways: those LangChain names, `openai_embeddings.create` under any import name or dotted path, the SDK's `embeddings.create`, a second `openai_client`, `getattr` and `import_module` of it; it is a guard, not a proof. Overriding `GatewayEmbeddings._embed` skips both the budget and the redaction. `Gateway.aclose` now closes the embeddings client.
   - **LangSmith.** The embeddings call makes no run of its own; the runs of a retriever or vector store around it are masked by the same process-wide client (item 6).

**What it does not do.** It is not anonymisation: a placeholder is a pseudonym, and the text sent can still be personal data (see the sources in 0006). It does not find every name, free-form address, special-category detail or text inside images (#97, #73; images are counted in `llm_unscanned_images`). Thinking blocks pass through unchanged, so a model's reasoning may show placeholders. A message's `name` cannot take a placeholder, so a call whose `name` holds personal data is refused (503, nothing sent). Text with no response format bound is taken as JSON (and its originals shown escaped) when it opens with `{` or with `[` and a non-letter; prose that opens with a footnote marker such as `[1]` is a rare, accepted misfire, and an array that opens with a letter (`[true]`) is missed. In a stream everything else is restored (text, tool-call arguments, refusals, the parsed object of a structured answer); only thinking and reasoning blocks stay as the model wrote them. A schema validator that rejects a placeholder (`EmailStr`, a pattern) fails inside the provider's SDK. Logs, errors and the 503 body carry only kinds, counts and error type names (`llm_redaction`, `redaction_allow_conflict`, `llm_redaction_failed`, `llm_unrestored_placeholders`, `llm_unscanned_images`); the `llm.redactions` metric is labelled by kind only.

**What you must do:**
1. Replace code that checks the type of `gateway.model()` with a check on `.inner`, or drop it.
2. Pass the values your app knows through `redaction_scope`, and show users the restored answer, never the placeholder: a `[EMAIL_1]` on screen is a bug.
3. Run `make migrate`, and the stamp-0005 step above if your database was stamped at 0006 without the column.
4. Re-embed the texts you stored (item 7), and embed documents and their queries under the same `redaction_scope`.
5. Read your prompts and tests: a test that asserts the exact text sent to a provider, or a cassette recorded with a prompt that holds personal-looking values, will see placeholders. `backend/tests/test_llm_redaction_wire.py` shows the pattern for a recorded call, and `tests/wire.py` a way to read the exact bytes a provider SDK sends without a network.

## Upgrading to 0.8.0

In order: 1. commit everything; 2. on 0.7.x, move your edits out of the old modules and fix the imports ("Old import paths removed" below); 3. `copier update --trust --defaults -a .copier-answers.fastapi.yml`; 4. delete `AGENT_MAX_STEPS` ("Agents give a final answer at their limit"); 5. `make lock && make install && make check`.

**New `llm` answer (#30).** Nothing to do on update: `copier update --trust --defaults` records `llm: langchain` for a project with the database and `llm: none` for one without, and, for a project with the database, changes five files: the answers file (the new `llm` line), `.claude/rules/fastapi.md`, the extras comment in `backend/pyproject.toml` (you own that file, so it can conflict), a comment in the project-root migration, and a new `backend/tests/test_llm_migrations.py`; a project without the database gets only the first three. The #34 steps below apply only with `llm: langchain`. The switch rule changed: `-d database=true` alone does not bring the gateway back once the answers file records `llm`, which the first 0.8.0 update does. A project from v0.7.1 with `database: false` has no recorded `llm` yet, so its first update with `-d database=true` gets the default `langchain` and the gateway returns: pass `-d llm=none` to keep it off. To turn it on, add `-d llm=langchain`; `-d database=false` also sets `llm: none`.

**Turning the gateway off** (`llm: none`, the database stays):

1. Commit everything first.
2. Tables are never dropped. To drop them, run `uv --directory backend run --locked --extra db --extra langchain alembic downgrade 0001` BEFORE updating (this also downgrades any of your own migrations that `depends_on` a gateway revision). Otherwise they stay, and `make migration` will not propose dropping them.
3. Run `copier update --trust --defaults -a .copier-answers.fastapi.yml -d llm=none`.
4. The update deletes `app/llm/` (including your `prices.py`, `checkpoint_types.py` and `redaction_rules.py`; recover them from git), `app/prompts/`, `llm-contracts.toml`, `tests/models.py`, `tests/recording.py`, `tests/wire.py`, the model tests, evals and cassettes. `app/models.py`, `migrations/env.py` and migrations 0002 to 0006 (twin files, like `main.py`, `settings.py`, `log.py`, `tests/conftest.py` and `.env.example`) change (they keep their revision ids, so the chain stays one line, and do nothing; expect conflicts if you edited them, and `app/models.py` very likely has your imports of the gateway's tables; untested). Your own code that imports `app.llm` fails `mypy`.
5. Remove `LLM_*`, `EMBEDDING_MODEL`, `*_API_KEY`, `AGENT_*` and `LANGSMITH_*` from `backend/.env` (leftovers are ignored). `langsmith[pytest]`, `vcrpy` and `pytest-recording` stay in the `dev` group, so `make install` still installs them.
6. Run `make lock && make install && make check`.

**Turning it on later:** `copier update --trust --defaults -a .copier-answers.fastapi.yml -d llm=langchain` (with no database: `-d database=true -d llm=langchain`). If a database never had the gateway's tables (it ran with `llm: none`, so migrations 0002 to 0006 did nothing and it is stamped at 0006), then AFTER that update (stamping first would make `make migrate` re-run the empty revisions and leave no tables), on every database the project runs against, production and staging included, and before you deploy the gateway, run `uv --directory backend run --locked --extra db --extra langchain alembic stamp 0001`, then `make migrate`. Without it `alembic upgrade heads` does nothing there and the app has no budget or checkpoint tables. A database that already has the tables needs only `make migrate`. A database that already had the gateway's tables and ran a release with 0006 under `llm: none` is stamped at 0006 without 0006's column: after turning the gateway back on, run `alembic stamp 0005` (instead of `0001`), then `make migrate`; see "Upgrading to 0.9.0" below. A later gateway migration will need the same step for a database stamped past it (decision 0005): downgrade to 0001 before turning the gateway off, or stamp the revision before it. `backend/tests/test_llm_migrations.py` runs this recipe against a real database.

**Agents give a final answer at their limit (#34, breaking).** The 422 at `AGENT_MAX_STEPS` is gone. An agent now makes at most `AGENT_MAX_MODEL_CALLS` model calls per run (default 13). The last call is made without tools, so the model writes a real answer. The result has `step_limit_reached` set (read it with `app.llm.langchain.steps.step_limit_reached(result)`) and the app logs `step_limit_reached` at warning level. The rule lives in `app/llm/core/steps.py`, so the Microsoft Agent Framework adapter (#35) will follow it too. `agent_step_limit` no longer exists: this is a deliberate change from 0.7.0's promise that log names stay unchanged, so update any alert that matches it. The final call is budgeted and recorded like any other call (its own reservation and `llm_call` row). The count is per run, not per thread: a run that resumes after a human-in-the-loop pause starts counting again.

Run against the real APIs on 9 Nov 2026 (the cheapest current model from each of OpenAI and Anthropic), three cases on each, a plain agent, a ToolStrategy and a ProviderStrategy, each with a second run on the saved thread: the last call with no tools was answered in every case except one. Anthropic with a ProviderStrategy and no tools got a 400 whose message was about a thinking block's signature (the cause was not isolated); with the tools kept and `tool_choice` set to `{"type": "none"}` it was answered, so that case uses that. AutoStrategy and other providers were not run against real APIs; an AutoStrategy is resolved as `create_agent` resolves it (by the model's profile or LangChain's list of model names).

**What you must do:**
1. Delete `AGENT_MAX_STEPS` from `backend/.env` and from every environment the app runs in. The app refuses to start while it is set, and the message says so: the old value V allowed ceil(V / 2) model calls, so the number cannot carry over.
2. Set `AGENT_MAX_MODEL_CALLS` only if you want something other than 13. The old default of 25 steps allowed 13 calls; setting 25 here would about double the worst-case spend of one looping run. A limit of 1 is allowed (the only call is the final answer).
3. Remove code that catches `StepLimitReached`, imports `step_limit_response` or expects a 422 from an agent. Both names were removed from `app.llm.core.errors`.
4. A `GraphRecursionError` is now a plain 500, treated as a bug (no handler any more). `gateway.agent()` sets LangGraph's `recursion_limit` only as a backstop, to `(2 + h) x N + a + 3` for N model calls, h before/after-model hooks and a before/after-agent hooks in your middleware (29 for the default).
5. Middleware passed to `gateway.agent(middleware=...)` runs outside the limit: it cannot offer tools again on the last call. A caller's `after_model` hook that jumps back to the model after the last call (`jump_to: "model"`) is your own loop: the middleware refuses to call the model past the limit, and the run fails with a plain 500 (a bug in your hook, not a limit). A ProviderStrategy answer that is not valid JSON raises inside `create_agent` on any call (a 500 after the call is billed); the limit does not change that. If its `wrap_model_call` retries or falls back, the extra provider calls count as one call against the limit, each has its own `llm_call` row, and `step_limit_reached` can be logged more than once. A run cut short with a `response_format` (ToolStrategy) ends after the last call even if the structured answer failed validation, so it may have no `structured_response`: check for it. If your own graph calls the model itself, count its calls and use `app.llm.core.steps.StepLimit`.
6. Show your users when an answer was cut short: check `step_limit_reached(result)`. The rules file says so.

## Upgrading to 0.7.1

0.7.1 loads saved agent threads strictly (#36). This is a behaviour change: saved objects of classes that are not listed come back as plain data. LangGraph's default loader reads a module name and a function name from a saved row, then imports and calls them (advisory GHSA-g48c-2wqr-h844). It needs someone who can already write to your database, so the risk is small, but closing it costs nothing. The checkpointer now rebuilds only what is on LangGraph's safe list (messages and their usage metadata, `Send`, `Command`, `Interrupt`, dates and times, UUIDs, decimals, sets, deques and a few more) plus the classes you list in `backend/src/app/llm/checkpoint_types.py`. Any other saved object comes back as its plain data (a dict, a list, or an enum's value) and LangGraph logs `Blocked deserialization of <module>.<name>` once per class and process.

**What you must do before you deploy 0.7.1:** nothing, if your agent state holds only messages and the types above (a normal `gateway.agent(...)` tool loop does). Otherwise list every class your graph keeps in its state in `ALLOWED`: pydantic models, dataclasses, Enums (nested ones too), a `response_format` model's `structured_response`, and the artifacts of `content_and_artifact` tools. The environment variable `LANGGRAPH_STRICT_MSGPACK` would derive these from the graph's state types in `StateGraph.compile`; this template sets strict loading in code instead (LangGraph reads the variable once, at import, and `backend/.env` does not reach the process in `make dev` or the tests), and an explicit setting gets no derived list, so nothing is listed until you list it. (`make eval` and `make record-llm` pass `--env-file`, so the variable could be set there, but the in-code setting does not follow it.)

Saved rows are not changed by the update. But a thread that runs again while its class is unlisted saves the plain-data form at its next checkpoint, and rolling back to an older release then does not bring the object back. List your classes before you deploy. `checkpoint_types.py` is yours to edit, like `prices.py`: it is not on the template-owned list, so your pull requests that change it raise no warning. It is read when the app opens the checkpointer, not when Alembic imports `checkpoints`; keep the classes you list in modules that import cheaply.

### The model gateway moved (#33)

0.7.0 moved the gateway's code into `app/llm/core/` and `app/llm/langchain/`. In 0.7.0 and 0.7.x the old import paths kept working with a `DeprecationWarning`; **0.8.0 removed them**. The mapping from each old path to its new one, how to find your uses and the patch targets are under "Old import paths removed" in "Upgrading to 0.8.0". The template runs pytest with `filterwarnings = error`, so while you are on 0.7.x one old import in app code (which conftest loads) stops the whole run at the first one. Names the 0.7.x modules did not forward (private helpers and names they only imported) are listed in the [v0.7.0 README](https://github.com/olaheavy-dev/house-template-fastapi/blob/v0.7.0/README.md).

`install_model_error_handlers` still registers only LangChain's and LangGraph's exceptions. If your own app factory (not the template's `main.py`) calls it, also call `app.llm.core.errors.install_failure_handlers(app)`, or a `ProviderError` becomes a plain 500 (0.7.0 also had a `StepLimitReached`; it was removed in 0.8.0, see "Upgrading to 0.8.0"). If your own migrations call `checkpoints.apply_migrations` (the rules tell projects to write them), import `from app.llm.langchain import checkpoints`, or conftest's in-process upgrade fails every database test. Scheduled jobs: change `python -m app.llm.report --expire-stale` to `python -m app.llm.core.report --expire-stale`; the old command no longer exists, and `make llm-report` already uses the new one.

**Signatures.** `token_details`, `settle(usage=)` and `record_call` take `app.llm.core.usage.Usage`, or `None` for no usage. `cost` takes a `Usage` only (`cost(price, None)` raises `AttributeError`), so skip pricing when there is no usage. A dict, even `{}`, raises `AttributeError` in all of them. Convert LangChain's usage with `from_langchain(usage) if usage else None` (`app.llm.langchain.usage`) where `None` is allowed. Inside a settlement the error is logged as `llm_settle_failed` and the reservation stays, so spend is over-recorded, never hidden.

**Overrides that change.** `BudgetGuard._settle` is no longer called (use `guard.meter`). On `GatewayEmbeddings`, `_settle` and `_batches` overrides are no longer called; `_embed` is still called but with a new signature `(texts, tags)` and does the whole metered call, so a v0.6.1 override `_embed(self, batch, *, feature, user_ref)` raises `TypeError` on every embeddings call: move it to `_create` (`MAX_INPUTS` and `MAX_BYTES` overrides still apply). A `Prompt.config()` override inside `gateway.call_config` is no longer called. A core `Prompt` does not equal a LangChain `Prompt` with the same fields: compare `.sha`.

**Behaviour changes** ([#66](https://github.com/olaheavy-dev/house-template-fastapi/pull/66), [#70](https://github.com/olaheavy-dev/house-template-fastapi/pull/70)). An embedding price's `max_prompt_tokens` now applies to every request: one text over the limit refuses the whole call with a 422 before anything is reserved (no shipped entry sets a limit). An unknown embeddings error is raised as itself, no longer as its own cause. An embeddings reply with no usage now closes its row `failed` at its reservation, where it used to stay `reserved`. If a provider error fits two failure kinds, the first matching kind decides whether the reservation is refunded, so spend can be over-recorded but never under-recorded.

**Unchanged:** the database schema and migrations (`migrations/env.py` and migration 0003 changed only import lines and comments), metric, log and problem names, HTTP bodies, rounding (up, once, on the total) and routes.

## Develop the template

To re-record the model cassette or run the evals here, put `OPENAI_API_KEY=...` (and optionally `LANGSMITH_API_KEY=...`) in `template/backend/.env`; the evals also need `LLM_MODEL` and `EMBEDDING_MODEL` there, while recording uses the models pinned in `tests/models.py`. The `.env` file is git-ignored and Copier never copies it. Then from `template/backend`:

```sh
env -u LLM_EVAL LLM_DAILY_BUDGET_USD=0.50 uv run --extra db --extra langchain --extra storage --env-file .env pytest -m vcr --record-mode=rewrite   # make record-llm
LLM_EVAL=1 LLM_DAILY_BUDGET_USD=1 uv run --extra db --extra langchain --extra storage --env-file .env pytest tests/evals -m eval   # make eval
```

`uv run pytest` renders the layer and checks it. CI also generates a real project from house-template-base plus this layer and runs its `make check`, once with the default answers and once per variant (`storage=false`; `llm=none` with the database, whose image holds none of the model packages and starts with no `backend/.env`; `database=false` with storage; `python_version=3.12`, the oldest supported Python; and `database=false storage=false`, whose `make check` runs with an unreachable `DOCKER_HOST` to show it needs no Docker, and which then starts the image with no `backend/.env` and calls `/health/ready`; every job also checks the backend runs on the Python its `.python-version` names). The variant jobs are not required checks yet: that is a repository-ruleset change for the owner. In `template/backend`, run `uv run --extra db --extra langchain --extra storage pytest` (the plain files next to each `.jinja` are the all-on twins; the extras they need are not in the default sync, and without them the tests fail to import `sqlalchemy` and the rest). On Python 3.14 the backend's langsmith pytest plugin raises a deprecation warning when it loads; one scoped filter in `template/backend/pyproject.toml` ignores that message until langsmith fixes it (#59). After changing `template/backend/pyproject.toml`, run `uv lock --directory template/backend`.

`main` is protected by [`.github/rulesets/main.json`](.github/rulesets/main.json): squash merges through pull requests, with the tests, workflow lint (actionlint and zizmor), the PR title check and CodeQL required, and CodeQL and zizmor findings blocking a merge. A test checks that every required check is a job the workflows run.

`tests/test_golden_render.py` keeps the default output from changing by accident: it renders `BASELINE_REF` (the latest release tag of this repository, v0.8.0 now) and the working tree with the default answers and compares every file, except what Dependabot maintains: `backend/uv.lock` is skipped and the tag or digest of the `image:` lines in `backend/compose/*/compose.yaml` is masked, so Dependabot PRs that change only `uv.lock` or an image tag or digest pass; one that edits `pyproject.toml` still needs an `INTENDED` entry. A feature PR that changes the default output on purpose adds the path to `INTENDED` with a reason and an issue number, and the test fails if a listed path no longer differs. A path-level entry hides a second, accidental change to the same file until the next baseline move. After each release, a `chore:` PR moves `BASELINE_REF` to the new tag and empties `INTENDED`. It needs the full git history (`git fetch --unshallow --tags` in a shallow clone).

Design records for choices every project inherits are in [`docs/decisions/`](docs/decisions/README.md).
